### 强制性评估数据分析（不可跳过）

## 输出格式要求

YAML 应包含两个部分：

1. **`spec:`** —— 任务规格说明。使用简洁的自然语言摘要并嵌入语义（如 `count: "2–4 matching + 0–1 distractors"`），而非原始观察值列表。在有助于理解的地方为关键结构添加 ASCII 图示。尽可能将对象/结构与任务标注中的标签对齐（如 src、dst、path、trajectory）。目标 ≤30 行。
2. **`generation_strategy:`** —— 描述如何构造有效输入。优先采用"输出优先，再反推"的方法：先构建完整输出（通常是约束更多的结构），然后通过逆转 `main()` 中描述的求解器变换来推导输入。这确保严格约束通过构造本身得到满足，而非通过随机试验（后者往往接受率接近于零）。按任务类型举例说明输出优先策略：
   - **move_to_match**：构建组装后的输出（dst 与 src 已附着/插入/填充/合并），然后拆离/拔出/分割并散布 src 以得到输入。
   - **move_along_path**：在输出中构建完整轨迹，然后放置 src 及任何反弹/转向结构，并移除轨迹以得到输入。

   **关键要求**：`transformation:` 中的每一个条件行为（如"若使用翻转则交换颜色"、"若 X 则 Y"）都**必须**作为 `generation_strategy:` 中的一个显式编号步骤出现，而不是仅在 spec 部分描述。generation_strategy 是生成器智能体将逐步实现的权威清单 —— 未列为步骤的内容很可能被跳过。同样，求解器所需的任何唯一性/消歧约束（如"只有一种颜色能匹配空腔大小"）必须作为 generation_strategy 中的显式步骤或约束出现，不能留为隐式。

总计目标 **≤40 行**。规格说明应简洁到人工可一目了然地审核。

**YAML 风格**：除非 YAML 语法要求，否则不要给字符串值加引号。写 `grid: 10-22 rows x 10-22 cols` 而非 `grid: "10-22 rows x 10-22 cols"`。多行内容使用 `|`。使用嵌套的 YAML 键按组件组织属性（如 `sprite:`、`frame:`、`ray:` 作为 `spec:` 下的顶层键，每个键下有子键）。不要将 `spec:` 或 `generation_strategy:` 写成单个 `|` 文本块。

**区分必需约束与观察到的约束**：如果某个属性不是求解器要求的，但在评估数据中是一致的模式（如所有精灵图恰好都是对称的），在规格说明中标记 `[observed]`。例如：`symmetry: LR and/or UD [observed]`。这告诉生成器作者这是锦上添花，不是硬性要求。反之，如果求解器硬编码或断言了某个值，则它是必需的 —— 不要标记 `[observed]`。

**约束应可量化且可验证**：优先使用 `spanning >=75% of rows and columns`（覆盖 >=75% 的行和列）而非 `meanders through most of the grid`（蜿蜒穿过大部分网格）。生成器的质量审计将以程序化方式检查每条约束 —— 模糊的描述无法被检查。

重要提示：所有分析请使用 `python` Python 解释器。编写脚本系统性地从评估数据中提取属性。要彻底 —— 检查那些你最初可能不认为重要的属性（对称性、规律性模式、颜色关系等）。
