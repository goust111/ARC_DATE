## 新题 7：形状匹配传色与对称轴门控

**组合逻辑**：[形状匹配](框内精灵体与框外精灵体形状比对) → [对称补全](创新：对称性作为门控条件——仅对称精灵体才接收传色) → [重涂色](通过传色的精灵体涂为框内参考色，未通过的保持原色)

**来源原语**：形状匹配/shape_matching + 空心矩形/hollow_rect + 框内参考色传同形/boxed_color_to_match + 重涂色/recolor(参考题 776ffc46)、对称补全/symmetry_completion + 双轴反射对称/biaxial_reflection_symmetry(参考题 0934a4d8, af22c60d)

**依赖链**：形状匹配建立框内外精灵体的对应关系；对称测试过滤出有资格接收传色的精灵体；传色只发生在同时满足"形状匹配"和"具有某种对称性"的精灵体上。两个条件缺一不可。

灰色框内有参考精灵体，框外有多个形状相同但颜色不同的副本。仅当框外副本自身具有水平或垂直镜像对称性时，才将其重涂为框内参考色；不对称的副本即使形状匹配也保持原色。

**输入结构**：约 20x20 的网格，背景为黑(0)。网格中有 2~3 个灰(5) 空心矩形框（边宽 1 像素，内部约 4x4 到 6x6）。每个框内部恰好有一个单色精灵体（颜色各不相同，取自蓝(1)、红(2)、绿(3) 等，精灵体为 4-连通不规则图形，3~8 像素）。框外散布若干单色精灵体（颜色取自黄(4)、橙(7)、品红(6) 等），其中一些与某个框内精灵体形状完全相同（含旋转 0 度，不考虑旋转匹配），另一些形状不匹配任何框内精灵体。在形状匹配的精灵体中，有些具有水平或垂直镜像对称性，有些不具有。生成约束：每个框内精灵体在框外至少有 1 个形状匹配且对称的副本和 1 个形状匹配但不对称的副本；不匹配任何框的精灵体至少有 1 个。

**规则**：
1. 识别灰(5) 矩形框和框内精灵体，建立"参考形状→参考颜色"映射。
2. 对每个框外精灵体，提取其形状掩码（像素相对位置集合），与所有框内参考形状做精确比对（不旋转，不翻转，仅平移匹配）。
3. 若形状匹配成功，进一步测试该框外精灵体的形状掩码是否具有水平镜像对称性或垂直镜像对称性（至少一种即可）。
4. 若形状匹配且具有对称性，则将该精灵体重涂为对应框内参考精灵体的颜色。
5. 若形状匹配但不具有对称性，保持原色不变。
6. 若形状不匹配任何框内精灵体，保持原色不变。
7. 灰(5) 框和框内精灵体保持不变。

**关键洞察**：形状匹配是必要条件但非充分条件，还需通过对称性门控测试。求解者必须对比多个示例才能发现"同形但不对称的副本为何未被传色"，从而归纳出对称性这个隐蔽条件。

2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。注意若描述中存在若干，需实现而不是只有单个，包括object或者对应关系等等。且若涉及到最短路径，则输入网格中必涉及到多条路径，对选择造成干扰。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。
5. 输出样例要视觉清晰，人类必须能从输入输出对中肉眼辨认出规律。具体要求：避免对象粘连、覆盖关系混乱、同一像素多重语义；不同逻辑步骤产生的结果不要大面积层叠在一起导致无法分辨哪个颜色属于哪个步骤；输入中各元素之间保持足够间距，输出中新增的标记/填充/路径等应与背景和已有元素在颜色上有明显区分；若规则涉及多层叠加，生成时控制对象密度和尺寸，确保叠加区域只占少数像素而非铺满整个网格。
6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现。分支概率不必平均——难以发现的隐蔽分支（如少数情况下才触发的特殊规则）应适当提高出现概率，确保在 3 个训练示例中至少出现一次，否则求解者无法归纳该规则。对于颜色映射类规则，确保 2 个左右的示例即可覆盖所有映射关系（每种颜色→颜色的映射至少在某个示例中出现过）。
7. 代码风格参考 `ARC_code`：使用 `numpy`，并把 `/home/lixinyu/snap/new/solvers/arc_utils.py` 作为公共参考工具箱，优先复用其中已经稳定的 bbox、连通域、裁剪、变换和颜色工具；目标文件必须能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，或从 `arc_utils.py` 摘取少量必要函数；若只实现一道题，优先保持目标文件自包含，减少额外依赖。
9. `main(grid)` 必须带一段 docstring，按 `ARC_code` 参考题的格式分四部分书写：首行用一句话概述转换目标；随后 `Input structure:` 描述输入网格中的对象/背景/标记/边界/组件；`Rule:` 给出从输入到输出的确定性变换规则；`Key insight:` 点明解题核心洞见。该 docstring 供下游相似度/索引流程（按 `main` 的 docstring 抽取机制标签）使用，缺失会导致此题无法被收录为参考题。
10. 网格尺寸必须符合 ARC 规范：`generate_input()` 产生的输入网格、以及 `main()` 返回的输出网格，行数和列数都必须 ≤ 30（即任何一维都不超过 30，整体不超过 30×30）。随机化网格大小时把上界封顶在 30；若规则会放大网格（如平铺、加边框、整数倍缩放），必须保证放大后的输出仍 ≤ 30×30，必要时收紧输入尺寸或放大倍数的随机范围，确保 100% 的随机样例都不越过 30×30。

执行每个代码生成 prompt 时，还必须遵守以下语义一致性硬约束：
1. 输出必须唯一可判定
   输入中的线索必须足以唯一确定目标对象、目标操作和结果。
   不允许依赖含糊解释，或让同一可见线索在不同语境下产生不同答案。
   注意不可多个不同样例的输入网格处理后的输出网格都相同
2. 组合步骤必须不可替代
   题目描述中的关键步骤都应对结果产生必要影响。
   不能让某一步只是表面存在，实际可被更简单的捷径完全替代。
3. 实现必须遵守题面定义的参照系
   所有判断、匹配、距离、对称、排序、分区等，都必须使用题面指定的对象范围和坐标参照。
   不得为了实现方便换成另一套参照系。
4. 生成样例要覆盖反例
   生成器要主动产生能排除错误捷径的样例。
   不只生成最容易通过的标准形态，还要覆盖边界情况、分支情况和易混淆情况。
5. 验证要检查语义而不只是自洽
   不能只验证 main(generate_input()) 能闭环。
   还要检查实现是否真的满足题面规则、关键依赖、唯一性和非退化性。
