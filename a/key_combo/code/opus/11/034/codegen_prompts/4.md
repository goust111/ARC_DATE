## 新题 4：种子分区镜像翻折

**组合逻辑**：[最近扩散→行分区](已有) + [镜像](创新：镜像轴不是预设的框架线，而是每个分区的种子条本身) + [等距异色为分隔](已有，但分隔行的处理从填单色变为填充混合标记)

**来源原语**：最近扩散、种子条、最近种子分区、等距异色为分隔(332202d5)；镜像、对称轴关系、框架为对称轴(f8a8fe49)；填充(93b581b8)

**依赖链**：种子条的位置决定最近分区→分区边界决定每段区域的范围→种子条同时充当该分区内内容的镜像轴→分区边界处等距于两个不同色种子的行需要特殊处理。分区与镜像通过种子条的双重角色（分区种子 + 对称轴）紧密耦合。

以彩色种子条为中心做最近分区，再在每个分区内将种子条一侧的图案镜像翻折到另一侧，等距异色边界行填为分隔色。

**输入结构**：黑(0)背景约 15x20 网格（高大于宽）。网格中有 2~3 条完整宽度的水平种子条，每条 1 像素厚，颜色互不相同（从红(2)、蓝(1)、绿(3)中取）。在每条种子条的上方紧邻区域（1~3 行），散布着若干橙(7)像素构成的小型不规则图案（4-连通，3~6 像素），这些图案只出现在种子条上方，种子条下方为纯黑(0)。种子条之间的间距不等（4~8 行）。生成约束：图案不跨越种子条；各种子条颜色互不相同。

**规则**：
1. 识别所有水平种子条及其颜色，按行位置排列。
2. 按最近种子条原则将所有非种子行分区：每一行归属于最近的种子条。
3. 对每个分区：找到该分区内种子条上方的橙(7)图案，以种子条所在行为镜像轴，将图案翻折到种子条下方对应位置（镜像复制）。原始图案保留不动。
4. 若某行到两条种子条的距离相等，且两条种子条颜色不同，则该行整行填充为灰(5)作为分隔行。
5. 若某行到两条种子条的距离相等，但两条种子条颜色相同（本题中不会发生，但规则需完备），则该行归属于上方的种子条。

**关键洞察**：种子条同时扮演两个角色——分区种子和镜像轴。仅看单个示例中一个种子条的行为，可能以为是简单的镜像；必须对比多个种子条的分区边界，才能归纳出"最近种子"分区规则以及等距异色行的分隔处理。

    color: single non-bg color shared by all sprites; chosen from {0,1,2,3,4,5,6,8,9} (any color != 7)
    size: exactly 3 pixels each (8-connected component)
    shapes: |
      Two canonical 3-pixel shapes (solver classifies by 4-neighbor corner degree):
        L-shape (axis-aligned right-angle, fills 3 corners of a 2x2 box):
          corner pixel has 2 4-neighbors; fires DIAGONALLY away from the missing 2x2 corner.
          Example: {(0,0),(0,1),(1,0)} -> missing (1,1); apex=(0,0); dir=(-1,-1) up-left
        V-shape (apex + two diagonal legs, spans 2 rows x 3 cols or 3 rows x 2 cols):
          apex has 2 8-neighbors (both diagonal); fires AXIS-ALIGNED opposite the opening.
          Example: {(0,1),(1,0),(1,2)} -> apex=(0,1); dir=(-1,0) up
    direction: 8 possible (4 diagonal for L, 4 axis for V); any mix of kinds and directions per grid
    separation: min Chebyshev distance between any two sprites >= 2 (no 8-connected merging)
  projectile:
    target_cell: apex + 5 * dir
    in_bounds: target must lie within the 16x16 grid for every sprite
  transform:
    grid_shape: same
    hit_sprite: if target cell lies on ANY sprite, recolor ENTIRE hit sprite to 9 (maroon)
    multi_hit_bg: if >=2 projectiles target the same EMPTY bg cell, paint that cell 1 (blue)
    lone_hit_bg: else a single projectile on an empty bg cell paints it 9 (maroon)
    preserve: unhit sprites keep their original color; untouched bg stays 7
  event_richness [observed]:
    at least one of {sprite-hit, multi-projectile collision} occurs per grid
    typical mix: 0-3 sprite hits, 0-2 collision points, rest are lone bg markers

generation_strategy:
  approach: output-first (place sprites + pre-chosen landing events, then erase landings for input)
  steps:
    - fix H=W=16, bg=7; pick sprite_color uniformly from {0,1,2,3,4,5,6,8,9}
    - decide sprite count N in [4,9] and a few events: e_hit in [0,2] (projectile hits another sprite), e_coll in [0,2] (2+ projectiles share a bg landing cell); remaining (N - #emitters_consumed_by_events) sprites land on unique empty bg cells
    - pre-sample sprite positions AND their (kind, direction) jointly so that every apex+5*dir lies in-bounds; reject placements that would make two sprites 8-adjacent (Chebyshev < 2)
    - for each "hit" event: pick a target sprite first, then add a shooter whose apex+5*dir lands on one of the target's 3 pixels (try all 8 directions; choose a kind compatible with that direction)
    - for each "collision" event: pick a bg cell, then add 2+ shooters whose apex+5*dir equals that cell
    - for remaining shooters: pick any apex+dir with target cell empty and not coinciding with other shooters' targets
    - paint sprites into the grid using the canonical L/V pixel patterns for each (kind,dir); do NOT paint any landing markers -> this is the input
    - run the solver to produce the expected output; assert: non-bg pixel count increases, at least one 9 and optionally 1 appears, and shape is preserved
