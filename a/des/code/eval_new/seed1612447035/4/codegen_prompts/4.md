- 每个交叉点的中心像素被替换为一个非 grey、非 bg 的颜色（red、blue、green 或 yellow 之一），该颜色编码了信号到达该交叉点时的转向规则。
- 路径网络的某一个末端有一个"信号源"标记：一个 orange 像素紧邻该路径末端像素（orange 像素本身不在路径上，而是与路径末端正交相邻）。
- 路径网络的若干其他末端各有一个"终点"标记：一个 maroon 像素紧邻路径末端。

Rule:
- 信号从 orange 信号源出发，进入其相邻的 grey 路径末端像素，初始传播方向为从 orange 像素指向该路径像素的方向。
- 信号沿路径直线传播（将经过的 grey 像素着色为 azure），直到遇到交叉点。
- 在交叉点处根据中心像素颜色转向：red = 向右转 90 度；blue = 向左转 90 度；green = 直行不转向；yellow = 掉头 180 度。转向以信号当前行进方向为参考。
- 信号沿新方向继续传播直到下一个交叉点或路径末端。
- 信号最终到达某个路径末端，该末端旁的 maroon 终点标记被重新着色为 orange，表示被"点亮"。其余 maroon 终点标记保持不变。

Key insight: 解题者需要先通过跨样例追踪信号的完整路径来破译四种颜色与转向方向的对应关系（这是一个需要多样例交叉验证的归纳过程），然后才能在新测试中模拟信号传播以确定哪个终点被点亮——颜色-转向映射关系的破译是核心难点。

## 实现要求

1. `main(grid)` 必须实现新题描述中的确定性转换规则，不能只识别 `generate_input()` 的固定模板。
2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。

6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现，即每个分支出现的概率平均，所谓的分支是在描述中提到的分支，即规则语义中的不同情况。
7. 代码风格参考 `ARC_code`：使用 `numpy`，必要时使用本地 helper，但目标文件应能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，但若只实现一道题，优先保持目标文件自包含，减少额外依赖。
