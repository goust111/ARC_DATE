- `description`：根据连接线的拓扑结构在节点之间传递颜色，节点颜色由其所有输入连接的颜色"混合"决定。
- `Input structure`：
  - 背景色为 Black。网格中有若干个 2x2 的彩色方块作为"节点"，每个节点为单一颜色。
  - 节点之间由 Grey 单像素宽的直线段（水平或垂直）连接。每条连接线段的一端紧邻一个节点，另一端紧邻另一个节点。
  - 部分节点为 Azure 色，称为"源节点"；其余节点为各种非 Azure、非 Grey、非 Black 的颜色，称为"混合节点"。
  - 网格右下角有一个小型"混合图例"：若干行，每行由两个颜色像素和一个箭头形 Grey 像素（在两色之间）组成，表示"颜色 A + 颜色 B → 结果色"。箭头指向的右侧有一个结果色像素。即每行格式为：[色A] [Grey] [色B] [Grey] [结果色]，共五个像素。
- `Rule`：
  - 第一步（网络解析）：识别所有节点和它们之间的 Grey 连接线段，构建连接关系。
  - 第二步（颜色传播）：每条 Grey 连接线段被重新着色为与其相邻的源节点颜色（如果连接线段两端都是源节点，则着色为离线段中点较近的那端的源节点颜色，中点像素归属于上方或左方的源节点）。如果连接线段一端是源节点、另一端是混合节点，则整条线段着色为源节点的颜色。
  - 第三步（节点混合）：对于每个混合节点，找到所有与之相连的连接线段的颜色（经过第二步着色后的颜色），如果恰好有两种不同颜色的连接线，则查阅混合图例找到对应的结果色，将该混合节点重新着色为结果色。如果只有一种颜色的连接线，混合节点着色为该颜色。源节点保持原色不变。
  - 混合图例在输出中保留不变。
- `Key insight`：解题的三层结构为：首先识别哪些是源节点（Azure 色）、哪些是混合节点；其次理解连接线段从源节点"继承"颜色的传播规则；最后发现混合节点根据图例将两种输入颜色合成为结果色。图例的"加色混合"语义是最隐蔽的机制层。

## 实现要求

1. `main(grid)` 必须实现新题描述中的确定性转换规则，不能只识别 `generate_input()` 的固定模板。
2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。
5. 输出样例要视觉清晰：避免对象粘连、覆盖关系混乱、同一像素多重语义、过密导致规则不可读。
6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现，即每个分支出现的概率平均，所谓的分支是在描述中提到的分支，即规则语义中的不同情况。
7. 代码风格参考 `ARC_code`：使用 `numpy`，必要时使用本地 helper，但目标文件应能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，但若只实现一道题，优先保持目标文件自包含，减少额外依赖。
