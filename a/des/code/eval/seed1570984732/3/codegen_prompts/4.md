- `Input structure`：
  - 背景色为 Black。网格中有若干条由 Grey 像素绘制的直线轨道（水平或垂直，宽度为 1 像素），轨道在若干位置交叉形成十字路口。
  - 每个十字路口的交叉像素被替换为一个彩色信号像素（Red、Blue、Green 或 Yellow 之一，非 Grey）。
  - 每条轨道的一个端点处（轨道的起始或末端，紧邻 Grey 像素的背景位置）放置一个 Maroon 单像素滑块。
  - 每条轨道的另一端（无滑块端）有一个 Orange 像素标记作为"终点墙"。

- `Rule`：
  - 每个滑块从其所在端点出发，沿轨道向 Orange 终点墙方向移动。
  - 滑块逐格前进，遇到 Grey 像素则继续，遇到 Orange 终点墙则停止。
  - 当滑块到达一个彩色信号像素（十字路口）时，滑块必须换轨：转向与当前行进方向垂直的那条轨道继续前进。换轨后行进方向在垂直方向的两个选择中，选择顺时针旋转 90 度的方向（Red 信号灯）或逆时针旋转 90 度的方向（Blue 信号灯）。
  - Green 信号灯表示滑块直行通过，不换轨。Yellow 信号灯表示滑块原地停止，不再移动。
  - 输出中，滑块从原位置消失，出现在最终停止位置，颜色仍为 Maroon。轨道和信号灯保持不变。

- `Key insight`：信号灯颜色不仅仅是标记——它们编码了换轨时的转向规则（顺时针/逆时针/直行/停止），解题者必须先从样例中归纳出每种颜色对应的转向语义，再模拟路径才能确定终点位置。这是一个"先破译信号编码、再执行路径模拟"的双层推理。

## 实现要求

1. `main(grid)` 必须实现新题描述中的确定性转换规则，不能只识别 `generate_input()` 的固定模板。
2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。

6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现，即每个分支出现的概率平均，所谓的分支是在描述中提到的分支，即规则语义中的不同情况。
7. 代码风格参考 `ARC_code`：使用 `numpy`，必要时使用本地 helper，但目标文件应能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，但若只实现一道题，优先保持目标文件自包含，减少额外依赖。
