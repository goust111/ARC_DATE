- `Input structure`：
  - 背景色 bg = azure。
  - 网格中散布着若干 2×2 的彩色方块，称为"交通灯"。每个交通灯由四个像素组成，其中三个像素颜色相同（灯体色），一个像素颜色不同（信号色），信号色像素在 2×2 方块中的位置（左上/右上/左下/右下）编码了转弯信息。
  - 网格的四条边上各有若干单像素的彩色起点标记（颜色非 bg、非任何灯体色），每个起点标记的颜色都是唯一的。
  - 每个起点标记所在的边决定了路径初始行进方向：上边→向下，下边→向上，左边→向右，右边→向左。

- `Rule`：
  - 从每个起点标记出发，沿初始方向画一条该起点颜色的直线路径（覆盖 bg 像素）。
  - 当路径前方遇到一个交通灯时，路径在交通灯边缘停止，然后转弯。转弯规则：信号色像素在 2×2 中的相对位置指示路径的出射方向——信号色在灯体的哪个角落，路径就从该角落的外侧沿垂直于入射方向的对应方向继续前进。具体而言：如果路径从左侧水平进入交通灯，信号色在右上角则路径向上转弯，信号色在右下角则路径向下转弯。其余入射方向类推（始终看入射面上信号色的相对位置来决定转向）。
  - 转弯后路径继续沿新方向直行，可能再次遇到交通灯并再次转弯，直到路径到达网格边界为止。
  - 交通灯本身不被路径覆盖，保持原样。

- `Key insight`：交通灯的转弯指令不是由灯体颜色决定的，而是由信号色像素在 2×2 方块内的空间位置编码的；需要结合路径的入射方向和信号色的角落位置来推断出射方向。

## 实现要求

1. `main(grid)` 必须实现新题描述中的确定性转换规则，不能只识别 `generate_input()` 的固定模板。
2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。
5. 输出样例要视觉清晰：避免对象粘连、覆盖关系混乱、同一像素多重语义、过密导致规则不可读。
6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现，即每个分支出现的概率平均，所谓的分支是在描述中提到的分支，即规则语义中的不同情况。
7. 代码风格参考 `ARC_code`：使用 `numpy`，必要时使用本地 helper，但目标文件应能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，但若只实现一道题，优先保持目标文件自包含，减少额外依赖。
