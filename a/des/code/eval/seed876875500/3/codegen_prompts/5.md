- `description`：在由 grey 网格线划分的棋盘格中，每个格子包含一个小型"种子图案"，根据种子图案的朝向确定生长方向，再根据相邻格子的种子颜色决定生长后的颜色混合结果。

- `Input structure`：
  - 背景色为 black。
  - grey 网格线将整个网格均匀分割为 R×C 个大小相同的正方形格子（每个格子内部为 N×N，N ≥ 3）。
  - 每个格子内部包含一个由单一颜色绘制的"种子图案"——一个 L 形（由 3 个像素组成的直角形状）。L 形的开口朝向四个方向之一（上/下/左/右），通过 L 形两臂的相对位置可识别朝向。
  - 种子图案的颜色从 red、blue、green、yellow、orange 中选取。

- `Rule`：
  - 第一层推理——识别生长方向：每个格子中 L 形的开口方向即为该格子的"生长方向"。例如 L 形开口朝右，则生长方向为右。
  - 第二层推理——颜色混合：沿每个格子的生长方向看向相邻格子。如果相邻格子存在（未超出网格边界），则该格子的"输出颜色"为：自身种子颜色。如果相邻格子不存在（生长方向指向网格边界外），则输出颜色为 maroon。如果两个相邻格子的生长方向互相指向对方（即格子 A 朝右生长，右边的格子 B 朝左生长），则这两个格子都使用 azure 作为输出颜色（互指覆盖规则优先级最高）。
  - 第三层推理——生长绘制：在输出中，每个格子内部的 L 形种子被移除，替换为一个从格子中心出发、沿生长方向延伸到格子边缘的矩形条带（宽度为 1 像素），条带使用该格子的"输出颜色"绘制。grey 网格线保持不变。

- `Key insight`：L 形的开口方向是生长方向的编码，而非 L 形的臂指向；互相对指的相邻格子对触发特殊颜色覆盖规则，需要全局扫描格子间的对称关系而非逐格独立处理。

## 实现要求

1. `main(grid)` 必须实现新题描述中的确定性转换规则，不能只识别 `generate_input()` 的固定模板。
2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。
5. 输出样例要视觉清晰：避免对象粘连、覆盖关系混乱、同一像素多重语义、过密导致规则不可读。
6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现，即每个分支出现的概率平均，所谓的分支是在描述中提到的分支，即规则语义中的不同情况。
7. 代码风格参考 `ARC_code`：使用 `numpy`，必要时使用本地 helper，但目标文件应能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，但若只实现一道题，优先保持目标文件自包含，减少额外依赖。
