- `Input structure`：
  - 背景色为 black。
  - 网格中有若干用 green 像素绘制的单像素宽路径段，路径段之间通过交叉点或拐角相连，形成一个有分叉的网络。
  - 路径网络中散布着若干"门"节点：每个门是一个 3×1 或 1×3 的小条，中心像素为 orange，两端像素中一端为 red、另一端为 black。门总是位于路径分叉点上，替换掉分叉点处的 green 像素。
  - 网络中有一个 yellow 像素作为信号源（起点）。
  - 路径的若干末端（死胡同）各有一个 azure 像素作为终端节点，初始状态为 azure。

- `Rule`：
  - 信号从 yellow 起点出发，沿 green 路径向所有可达方向同时传播。
  - 当信号到达一个门节点时，观察门的 red 端指向哪个方向：信号只能从 red 端所指的那一侧继续传播，另一侧被阻断。即信号从门的一侧进入后，只有 red 端朝向的出口方向可以通过。
  - 如果信号从 red 端所指方向进入门，则信号被阻断，不能通过该门。门是单向的：只允许信号从非 red 端进入、从 red 端方向离开。
  - 信号最终到达的所有终端节点（azure 像素）变为 magenta；未被信号到达的终端节点保持 azure。
  - 路径、门、起点在输出中保持不变，仅终端节点颜色可能改变。

- `Key insight`：解题者首先需要识别出门节点的结构并理解 red 端标示的是允许通过的出口方向（方向编码层），然后需要在整个网络中追踪信号的可达性，考虑门的单向性导致的路径剪枝（网络传播层）。门的朝向决定了哪些终端可达，而非简单的连通性判断。
</new_puzzle>

## 实现要求

1. `main(grid)` 必须实现新题描述中的确定性转换规则，不能只识别 `generate_input()` 的固定模板。
2. `generate_input()` 必须随机生成多样样例，不能固定死。随机维度应覆盖：网格大小、对象数量、位置、颜色、方向、形状参数或关键分支。
3. 生成器必须保证输入满足 `main()` 的隐式假设：对象不重叠、不越界、特殊标记唯一或可区分、匹配关系无歧义、关键分支出现概率相同。
4. 禁止把 ARC 颜色 id 、亮度、拼写等当作人类不可见的数值语义参与排序、大小比较或隐藏映射。颜色变化必须有可见结构线索。注意颜色亮度、拼写等也是不可见信息，若描述中出现违规的颜色id或者亮度，可自行使用少量的固定颜色替代，但注意生成时要在三个以内输入输出网格中对所有变换100%覆盖度。
5. 输出样例要视觉清晰：避免对象粘连、覆盖关系混乱、同一像素多重语义、过密导致规则不可读。
6. 若规则有多个分支，生成器不能长期固定成一个分支；应让分支在随机样例中合理出现，即每个分支出现的概率平均，所谓的分支是在描述中提到的分支，即规则语义中的不同情况。
7. 代码风格参考 `ARC_code`：使用 `numpy`，必要时使用本地 helper，但目标文件应能被 `SourceFileLoader` 直接加载。
8. 可以在目标目录放公共 helper 文件，但若只实现一道题，优先保持目标文件自包含，减少额外依赖。
